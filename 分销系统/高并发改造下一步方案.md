# 分销系统高并发改造下一步方案

## 1. 文档目的

这份文档用于指导当前分销系统从“具备基础异步能力”升级到“可支撑中高并发访问”的工程化状态。

本文档不包含代码实现，重点是：

- 明确当前系统距离高并发还有哪些关键差距
- 给出下一步的改造顺序
- 帮助团队按阶段推进，而不是一次性大改
- 为后续压测、上线、验收提供统一标准

---

## 2. 当前项目的并发现状判断

当前后端已经具备一定的并发基础：

- 使用 `FastAPI`
- 数据库访问使用异步 SQLAlchemy
- 微信接口和 AI 接口使用异步 HTTP 客户端

但当前系统还不能定义为“已经实现高并发”，原因主要有以下几类：

- 部署层仍偏单实例/单进程思路，缺少多 worker、多实例、负载均衡设计
- 限流、缓存、AI 会话状态仍存在进程内存中，无法支持水平扩展
- 某些核心业务仍是“先查再写”，并发下容易出现重复写入、重复计分、丢更新
- 热点接口仍有全量查询、应用层排序、随机排序等高成本操作
- 外部依赖较多，包括微信接口、AI 接口、对象存储，这些慢调用在高并发下容易拖垮整体响应
- 尚未看到完整的压测、容量评估、监控告警闭环

结论：

当前系统属于“中小流量可运行的异步项目”，还未进入“高并发可验证、可扩展、可治理”的阶段。

---

## 3. 改造目标

建议把高并发目标拆成三个层次：

### 3.1 正确性目标

在并发访问时，系统不能出现以下问题：

- 同一用户重复提交被重复记分
- 每日题目在高峰时段被重复生成
- 用户积分被并发覆盖导致少加分
- 限流失效
- AI 会话状态错乱

### 3.2 性能目标

核心接口在目标并发下保持稳定：

- 登录接口可稳定处理突发登录流量
- 每周答题和提交接口可稳定处理晚间高峰
- 排行榜接口不会因数据量增长而明显恶化
- AI 问答接口不会拖慢其他普通业务接口

### 3.3 工程目标

系统具备可持续扩容能力：

- 能从单实例扩展到多实例
- 能通过缓存和数据库优化支撑增长
- 能通过压测和监控判断瓶颈位置
- 能在出现外部依赖波动时进行降级

---

## 4. 改造原则

高并发改造建议遵循以下原则：

- 先保证并发正确性，再追求更高吞吐
- 先改热点路径，再改边缘接口
- 先解决架构级问题，再做局部微优化
- 先可观测，再扩容
- 先分阶段交付，再做长期演进

不建议一开始就做“大重构”。

更适合当前项目的方式是：

- 第一阶段修复并发风险
- 第二阶段提升吞吐能力
- 第三阶段补齐稳定性与压测闭环

---

## 5. 下一步总体路线

建议分为四个阶段推进。

### 阶段一：并发正确性治理

这是最优先的阶段。

如果这一阶段不做，系统即使能承受更多请求，也可能在高并发下出现错账、重复提交、状态错乱。

本阶段重点：

- 把进程内状态迁移到 Redis
- 把关键业务写操作改为数据库原子保证
- 给关键业务补幂等设计
- 给热点写接口加事务和冲突处理

核心任务：

- 限流从本地内存迁移为 Redis 分布式限流
- 微信 `access_token` 缓存迁移到 Redis
- AI 会话状态迁移到 Redis 或数据库
- 每日题目生成增加唯一性保护与冲突处理
- 每周答题提交增加唯一提交约束
- 用户积分改为数据库原子累加，而不是先读后写
- 上传、外部 API 调用失败时定义明确重试和失败返回策略

阶段一完成标准：

- 多实例部署后，限流仍然有效
- 同一业务请求重复到达不会重复记分
- 高峰时段不会产生多条当日题目记录
- 并发下用户总分不会丢失更新

### 阶段二：吞吐能力提升

阶段一解决的是“不会错”，阶段二解决的是“能扛住”。

本阶段重点：

- 改造部署拓扑
- 提升数据库承载能力
- 改造高成本查询
- 引入缓存

核心任务：

- 服务部署改为多 worker
- 增加负载均衡层
- 服务设计为无状态，允许多实例水平扩容
- 明确数据库连接池参数
- 审核热点表索引
- 排行榜改为数据库排序或缓存排行
- 随机抽题改为题库预选池或缓存题目 ID
- 学习记录和统计接口改为分页和数据库聚合
- 首页、排行榜、个人排名、每日题目等读多写少接口接入缓存

阶段二完成标准：

- 单实例扩展为多实例后，系统行为保持一致
- 排行榜和首页类接口响应时间稳定
- 数据量增长后，题目抽取和记录查询不会明显退化
- 数据库连接数、慢查询数量在可控范围内

### 阶段三：稳定性与隔离能力建设

高并发系统不仅要快，还要能在异常情况下撑住。

本阶段重点：

- 给慢依赖做隔离
- 给高成本能力做降级
- 给系统加完整监控

核心任务：

- AI 问答接口单独限流
- AI 接口增加超时、熔断、降级提示
- 微信接口调用增加失败重试策略和错误分级
- 对象存储上传链路做异步化或后台处理评估
- 非强实时任务考虑引入消息队列
- 建立接口耗时、错误率、QPS、数据库连接池、Redis 命中率监控
- 为高峰期设置告警阈值

阶段三完成标准：

- AI 服务异常时不会拖垮普通答题业务
- 外部接口超时不会引发整体雪崩
- 线上能快速定位性能瓶颈和故障点

### 阶段四：压测与容量评估

没有压测，就无法证明系统真正具备高并发能力。

本阶段重点：

- 搭建压测场景
- 根据压测结果继续回优化
- 给出容量结论

建议压测场景：

- 登录场景
- 每周答题查询场景
- 每周答题提交通道场景
- 排行榜查询场景
- AI 问答场景
- 混合流量场景

建议观测指标：

- 平均响应时间
- P95 响应时间
- P99 响应时间
- 错误率
- 429 比例
- 数据库连接池占用
- Redis 延迟和命中率
- CPU、内存、网络带宽

阶段四完成标准：

- 可以明确回答系统在当前架构下能支撑多少并发用户
- 能识别瓶颈是在应用、数据库、缓存、还是外部依赖
- 可以给出扩容建议，而不是只靠经验判断

## 6. 针对当前项目的优先级建议

如果只看“下一步最值得做什么”，建议按下面顺序执行。

### P0：必须先做

- 引入 Redis，统一承接限流、缓存、会话状态
- 修复每周答题、题目轮次、积分累计的并发一致性
- 明确生产环境必须使用 MySQL，不再依赖 SQLite 或内存模式
- 补全关键业务的唯一约束、事务与幂等策略

### P1：紧接着做

- 改造部署方式，支持多 worker、多实例
- 审核数据库连接池配置
- 优化排行榜、个人排名、学习记录、题目随机抽取
- 把首页和排行榜类热点查询接缓存

### P2：随后做

- AI 服务限流、隔离、降级
- 上传链路异步化评估
- 引入监控、告警、慢查询分析
- 开始压测并基于结果调优

### P3：中期演进

- 对统计类接口做预计算
- 对非实时任务引入消息队列
- 按业务域考虑拆分 AI 服务、用户服务、学习服务

---

## 7. 推荐的目标架构

结合当前项目，推荐的中期架构如下：

- 微信小程序作为前端入口
- 负载均衡层负责流量分发
- FastAPI 服务多实例部署
- Redis 负责限流、热点缓存、会话状态、分布式锁
- MySQL 负责核心事务数据
- 对象存储负责头像等静态资源
- AI 服务调用与普通业务流量隔离
- 监控系统负责指标采集、日志检索、告警通知

这套架构的核心思想是：

- 应用层无状态
- 状态统一外置
- 热点请求优先缓存
- 写操作优先保证原子性
- 慢依赖与核心交易路径隔离

---

## 8. 一周内可落地的执行清单

如果希望尽快启动，建议第一周只做下面这些事。

### 第 1 天到第 2 天

- 明确生产环境当前实际部署方式
- 统计核心接口清单
- 识别高峰时段和高峰流量入口
- 定义本次高并发改造的验收指标

输出物：

- 核心接口列表
- 高峰流量路径图
- 初版性能目标表

### 第 3 天到第 4 天

- 确定 Redis 引入方案
- 列出所有当前使用进程内状态的模块
- 梳理所有“先查再写”的关键业务点
- 确定数据库唯一约束和事务策略

输出物：

- Redis 使用清单
- 并发风险点清单
- 数据一致性改造清单

### 第 5 天到第 7 天

- 完成第一批并发正确性改造设计
- 确定多 worker 和多实例部署方案
- 确定压测工具和压测场景
- 建立最小监控面板

输出物：

- 第一阶段改造方案评审稿
- 部署拓扑图
- 压测计划
- 监控指标清单

## 9. 一个月内建议完成的里程碑

### 第 1 周

- 完成并发正确性方案设计
- 落实 Redis 引入与业务拆分策略

### 第 2 周

- 完成热点写路径改造
- 完成多实例部署准备

### 第 3 周

- 完成热点读路径缓存与查询优化
- 完成监控与告警接入

### 第 4 周

- 完成压测
- 根据压测结果优化一次
- 形成容量评估报告

## 10. 验收标准

高并发改造是否有效，建议按以下标准验收。

### 功能正确性

- 没有重复答题计分
- 没有积分丢失
- 没有每日题目重复生成
- 多实例情况下用户状态一致

### 性能稳定性

- 核心接口在目标并发下错误率可控
- 排行榜和首页接口耗时稳定
- AI 慢调用不会显著影响其他业务

### 工程可运维性

- 有完整监控面板
- 有慢查询定位能力
- 有压测报告
- 有扩容建议

---

## 11. 当前阶段不建议优先投入的事项

为了避免改造失焦，以下内容不建议放在当前最前面：

- 过早拆成很多微服务
- 过早做复杂的事件驱动架构
- 先做大量前端优化而忽略后端一致性
- 在没有压测数据前盲目加机器
- 在没有缓存治理前直接放大数据库压力

---

## 12. 最终建议

对当前项目来说，下一步不是立刻追求“几万并发”，而是先把系统升级到“多实例下仍然正确、热点路径可优化、外部依赖可隔离、可以用压测验证”的状态。

因此，最推荐的起步顺序是：

1. 先引入 Redis，统一处理分布式限流、缓存和会话状态
2. 先修复每周答题、积分累计、题目轮次生成的并发一致性
3. 再改造部署与数据库承载能力
4. 再优化排行榜、抽题、学习记录等热点查询
5. 最后用压测和监控闭环验证高并发能力

如果上述顺序执行到位，这个项目就会从“异步项目”真正迈向“可扩展的高并发项目”。
